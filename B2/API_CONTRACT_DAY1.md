# BE2 Day 1 API contract — PROPOSED, NOT YET TEAM-SIGNED

This draft is based on the revised 24 October work-distribution PDF. It is not a locked contract. BE1, FE1, FE2 and the leader should confirm route names, ID mapping, role permissions, shared `as_of` date and fields before wiring screens.

## Safety/integration rules

- Every response and demo record is labelled `SYNTHETIC DATA / PROPOSED INTEGRATION`.
- An actor is resolved by the backend from a demo identity; a request cannot choose its own role or centre scope. The demo identity is not real authentication and must not be exposed as production security.
- Centre scope is checked server-side for every beneficiary/task/flag request. Missing centre mapping fails closed; no default centre is invented.
- A flag is not a diagnosis. Original measurement records are immutable; remeasurement is appended with a new ID and a parent/original-record link.
- AI endpoints are deterministic mock-first and use only saved flag, rule, measurement and timeline records. They do not make eligibility/treatment/permission/closure decisions.
- Counts are computed by normal code from saved records, not generated by an LLM.
- One `as_of` date is passed to date-sensitive endpoints; initial demo default follows `B2.demo_clock.DEFAULT_DEMO_DATE` until BE1/team agrees another configuration.

## Proposed Day 1 routes

| Method and route | Purpose |
|---|---|
| `GET /api/health` | Report service mode and seeded synthetic status; no key/secret exposure. |
| `GET /api/cases/{beneficiary_id}/explain?flag_id=...` | Explain one saved flag with its rule ID/version, recorded source values, missing fields and a mock explanation. |
| `GET /api/beneficiaries/{beneficiary_id}/history` | Build a summary/timeline from saved original and remeasurement records, flags, tasks and audit events; each item links to its source record ID. |
| `POST /api/verification` | Save a remeasurement as a new immutable record, run BE1 data checks/rules, return the new check/result and a history link. Never overwrite the source measurement. |
| `POST /api/tasks` | Create a task from a saved flag and its existing beneficiary/centre scope. |
| `POST /api/tasks/{task_id}/actions` | Apply one allowed transition; append an audit event for the action. |
| `POST /api/next-actions/{flag_id}/decision` | Save `accept`, `edit` or `reject`; an accepted operational action must call the normal task API/service and cannot close a task. |
| `GET /api/briefing?centre_id=...&as_of=YYYY-MM-DD` | Deterministic counts and case links for a centre/date. A non-AI briefing is the first version. |

## Proposed request conventions

- Demo actor: `X-Demo-Actor` header; backend resolves this against a server-side, synthetic allow-list. The client does not send `role` or arbitrary `centre_ids`.
- Common error response: `{"error":{"code":"...","message":"...","retryable":false}}`.
- Suggested task states: `open`, `assigned`, `acknowledged`, `in_progress`, `escalated`, `closed`; exact allowed transitions require FE/team sign-off.
- IDs: use current source IDs unchanged until BE1 confirms migration. Current `B1/children.csv` uses `C0001` and has no `centre_id`; the new document proposes IDs such as `BEN-0001` and centre IDs such as `AWC-001`. Do not silently map or fabricate a centre.
- Demo fixture exception: `api.py` explicitly labels its local C0001 → AWC-001 assignment as synthetic-only so tests can exercise centre permissions. This is not source data, not team-approved, and must be replaced by BE1's actual fixture mapping before integration.
